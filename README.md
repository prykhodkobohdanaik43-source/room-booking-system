# Система бронювання переговорних кімнат в офісі

Внутрішній веб-застосунок компанії (~60 співробітників, 5 переговорних кімнат на 4–20 місць).
Замінює спільний Google-календар: показує, яка кімната вільна просто зараз, не дає створити дві
броні на той самий час і звільняє кімнату, якщо на зустріч ніхто не прийшов.

Навчальний проєкт, група ІК-43. Базова структура коду за архітектурою з лабораторної роботи №2.

- Крупко Софія — фронтенд (React)
- Приходько Богдана — тімлід, база даних і тестування
- Русанова Вікторія — бекенд (Node.js, Express)

## Запуск

Потрібні Node.js 22+ і PostgreSQL 16 (або Docker).

```bash
npm install
cp .env.example .env
docker compose up -d db     # або власний PostgreSQL
npm run db:migrate
npm run db:seed             # 5 кімнат і 4 облікові записи, пароль Passw0rd!
npm run dev                 # API :3000, інтерфейс :5173
```

Без `DATABASE_URL` застосунок стартує зі сховищем у пам'яті — зручно, щоб подивитися інтерфейс,
але дані зникають після перезапуску.

Демо-облікові записи: `olena.kovalenko@example.com` (співробітник),
`iryna.melnyk@example.com` (адміністратор офісу), `taras.shevchuk@example.com` (IT).

Уся система в контейнерах: `docker compose up --build`.

## Структура проєкту

```
src/backend/
  config/          читання змінних середовища в один незмінний об'єкт
  db/              міграції, запуск міграцій, seed, пул з'єднань
  modules/
    auth/          вхід, хешування паролів, JWT, посилання на встановлення пароля
    users/         облікові записи, ролі
    rooms/         довідник кімнат
    bookings/      броні: сутність, правила, сервіс, контролер
      rules/       окреме правило на кожну перевірку (час, горизонт, кімната, місткість)
    eventlog/      журнал подій
    notifications/ листи (SMTP або консоль)
    scheduler/     фонові задачі: автоскасування, нагадування
  shared/          помилки, годинник, робота з датами, middleware
  app.js           складання Express-застосунку з роутерів модулів
  container.js     створення й з'єднання всіх об'єктів (composition root)
  server.js        точка входу

src/frontend/src/
  api/             HTTP-клієнт і виклики REST API
  auth/            контекст автентифікації, захист маршрутів
  components/      layout та дрібні елементи форм
  pages/           екрани: вхід, стан кімнат, розклад, бронювання, кімнати
  styles/          стилі

tests/
  backend/unit/         сутності та правила без бази й мережі
  backend/contract/     спільний набір перевірок для обох репозиторіїв броней
  backend/integration/  сценарії 1–5 через HTTP
  frontend/             компоненти React
  helpers/              тестовий застосунок, фіксований годинник, підміни

docs/                нотатки до структури коду
```

Кожен модуль — окрема папка з власною сутністю, репозиторієм, сервісом, контролером і
маршрутами. Модулі спілкуються через сервіси, а не через чужі репозиторії.

## Як дотримані принципи SOLID

**S.** Сутність `Booking` відповідає за переходи станів броні, `BookingService` — за роботу зі
сховищем і сповіщеннями, `BookingController` — лише за HTTP. Кожне правило бронювання (час,
горизонт, доступність кімнати, місткість) — окремий клас з однією причиною для змін.

**O.** Нову перевірку при бронюванні додають новим класом-нащадком `BookingRule` і одним рядком у
`defaultBookingRules()`; `BookingService` при цьому не змінюється. Так само додають задачу
планувальника або канал сповіщень.

**L.** `InMemoryBookingRepository` і `PgBookingRepository` взаємозамінні: обидва проходять той
самий набір перевірок `tests/backend/contract/bookingRepositoryContract.js`. Тому тести бізнес-логіки
працюють зі сховищем у пам'яті, а поведінка лишається тією самою, що й з PostgreSQL.

**I.** Інтерфейси вузькі: `PasswordHasher` — це `hash`/`verify`, `NotificationChannel` — один метод
`send`, `Clock` — один метод `now`. Тестові підміни реалізують рівно ці методи.

**D.** `BookingService` залежить від абстракцій `BookingRepository`, `NotificationChannel`, `Clock`,
а не від `pg`, `nodemailer` чи системного часу. Конкретні реалізації обирає `container.js`, тому
заміна бази чи поштового сервера не зачіпає бізнес-логіку.

## Заборона накладення броней

Головна вимога замовника (ФВ-18) тримається на обмеженні рівня бази даних, а не лише на коді:

```sql
CONSTRAINT bookings_no_overlap EXCLUDE USING gist (
    room_id WITH =,
    tstzrange(start_time, end_time, '[)') WITH &&
) WHERE (status IN ('ACTIVE', 'CONFIRMED'))
```

Навіть якщо два запити надійдуть одночасно, PostgreSQL прийме рівно один, а другий отримає помилку
`23P01`, яку `PgBookingRepository` перетворює на `SlotTakenError` і відповідь `409 Conflict`.
Сценарій 2 зі специфікації вимог перевіряють тести контракту й інтеграційний тест.

## Робота з Git

- `main` — захищена гілка, у неї потрапляє лише злитий pull request;
- гілки формату `feature/<модуль>-<задача>`, наприклад `feature/bookings-core`;
- одна задача з дошки Trello — одна гілка й один pull request;
- перед злиттям — код-рев'ю іншою учасницею команди та зелений CI
  (ESLint, Prettier, тести, збірка фронтенду).
