# Структура коду

Документ пояснює, з яких класів складається система і як вони пов'язані з діаграмами
лабораторної роботи №2.

## Модулі бекенду

Поділ повторює компонентну діаграму (рис. 1 лаб. №2).

| Модуль          | Головні класи                                                   | Вимоги                                                   |
| --------------- | --------------------------------------------------------------- | -------------------------------------------------------- |
| `auth`          | `AuthService`, `BcryptPasswordHasher`, `JwtTokenService`        | ФВ-01, ФВ-16, НФВ-06, НФВ-15, ОБМ-03                     |
| `users`         | `User`, `UserService`, `UserRepository`                         | ФВ-16, ФВ-17, ФВ-29                                      |
| `rooms`         | `Room`, `RoomService`, `RoomRepository`                         | ФВ-13 – ФВ-15, ФВ-19                                     |
| `bookings`      | `Booking`, `BookingService`, `BookingRepository`, `BookingRule` | ФВ-02, ФВ-04 – ФВ-08, ФВ-18 – ФВ-20, ФВ-23, ФВ-27, ФВ-28 |
| `eventlog`      | `EventLogEntry`, `EventLogService`                              | ФВ-22                                                    |
| `notifications` | `NotificationService`, `NotificationChannel`                    | ФВ-16, ФВ-21, ФВ-25                                      |
| `scheduler`     | `Scheduler`, `AutoCancelJob`, `ReminderJob`                     | ФВ-20, ФВ-21, НФВ-07                                     |

Кожен модуль містить одну-дві сутності, абстрактний репозиторій із двома реалізаціями
(в пам'яті та PostgreSQL), сервіс з бізнес-логікою, контролер і файл маршрутів.

## Доменна модель

Класи відповідають діаграмі класів (рис. 3 лаб. №2).

- `User` — обліковий запис: `authenticate()`, `block()`, `unblock()`, лічильник невдалих спроб входу
  для НФВ-15.
- `Role` — перелічення `EMPLOYEE`, `OFFICE_ADMIN`, `IT`.
- `Room` — кімната: `update()`, `deactivate()`, `isAvailable()`, `fits()`.
- `Booking` — бронь: `create()`, `cancel()`, `confirmArrival()`, `autoCancel()`, `overlaps()`.
- `BookingStatus` — перелічення `ACTIVE`, `CONFIRMED`, `CANCELLED`, `AUTO_CANCELLED`.
- `EventLogEntry` — запис журналу; `actorId = null` означає дію системи.

## Життєвий цикл броні

Переходи повторюють діаграму станів (рис. 5 лаб. №2):

```
                   відмітка про прихід (ФВ-08)
        ┌─────────────────────────────────────────► CONFIRMED
        │
     ACTIVE ──── скасування автором / адміністратором ──► CANCELLED
        │                                (ФВ-06, ФВ-10)
        └──── 10 хвилин без відмітки (ФВ-20) ──────────► AUTO_CANCELLED
```

Слот вважається зайнятим, поки бронь у статусі `ACTIVE` або `CONFIRMED`. Перевірка часу перебуває
у двох місцях: `Booking.overlaps()` — у коді, обмеження `bookings_no_overlap` — у базі даних.

## Порядок перевірок при створенні броні

Послідовність з діаграми послідовностей (рис. 4 лаб. №2):

1. `Booking.create()` — обов'язкові поля, коректні дати, кількість учасників від 1 (ФВ-05).
2. `TimeRangeRule` — завершення пізніше за початок (ФВ-04).
3. `HorizonRule` — не в минулому й не далі ніж на 28 днів (ФВ-27).
4. `RoomAvailabilityRule` — кімната активна на цю дату (ФВ-15).
5. `CapacityRule` — учасників не більше за місткість; відповідь `422` ще до звернення до
   таблиці броней (ФВ-19).
6. `INSERT` у базу; конфлікт часу вирішує обмеження `EXCLUDE`, звідси `409` (ФВ-18).
7. Запис події у журнал (ФВ-22).

## REST API

Усі маршрути, крім `/api/health`, вимагають заголовок `Authorization: Bearer <токен>`.

| Метод | Маршрут                             | Роль                      | Вимога       |
| ----- | ----------------------------------- | ------------------------- | ------------ |
| POST  | `/api/auth/login`                   | —                         | ФВ-01        |
| POST  | `/api/auth/set-password`            | —                         | ФВ-16        |
| GET   | `/api/auth/me`                      | будь-яка                  | —            |
| GET   | `/api/schedule?date=YYYY-MM-DD`     | співробітник, адмін офісу | ФВ-02        |
| GET   | `/api/schedule/now`                 | співробітник, адмін офісу | ФВ-23        |
| POST  | `/api/bookings`                     | співробітник, адмін офісу | ФВ-04        |
| POST  | `/api/bookings/:id/cancel`          | співробітник, адмін офісу | ФВ-06, ФВ-10 |
| POST  | `/api/bookings/:id/confirm-arrival` | автор броні               | ФВ-08        |
| GET   | `/api/rooms`                        | будь-яка                  | ФВ-02        |
| POST  | `/api/rooms`                        | IT, адмін офісу           | ФВ-13        |
| PATCH | `/api/rooms/:id`                    | IT, адмін офісу           | ФВ-14        |
| POST  | `/api/rooms/:id/deactivate`         | IT, адмін офісу           | ФВ-15        |
| GET   | `/api/users`                        | IT                        | ФВ-16        |
| POST  | `/api/users`                        | IT                        | ФВ-16        |
| POST  | `/api/users/:id/block`              | IT                        | ФВ-17        |
| POST  | `/api/users/:id/unblock`            | IT                        | ФВ-17        |

Помилки завжди мають однакову форму:

```json
{ "error": { "code": "SLOT_TAKEN", "message": "Слот уже зайнято" } }
```

| Код | Коли                                                          |
| --- | ------------------------------------------------------------- |
| 401 | немає токена, токен недійсний або обліковий запис заблоковано |
| 403 | роль не має права на дію (ФВ-28, ФВ-29)                       |
| 404 | кімнати, броні або маршруту не існує                          |
| 409 | слот зайнято, вікно відмітки закрите, бронь уже не активна    |
| 422 | некоректні дані: місткість, горизонт, відсутня причина        |

## Схема бази даних

`src/backend/db/migrations/001_init.sql`: таблиці `users`, `rooms`, `bookings`, `event_log`.
Ключові обмеження:

- `rooms_name_unique` — унікальна назва кімнати без урахування регістру (ФВ-13);
- `capacity > 0`, `participants_count >= 1`, `end_time > start_time`;
- `bookings_no_overlap` — `EXCLUDE USING gist` для заборони перетину броней (ФВ-18);
- `bookings_status_start_idx` — індекс для вибірок планувальника.

Міграції застосовує `npm run db:migrate`; застосовані файли фіксуються в таблиці
`schema_migrations`.

## Тести

| Набір                       | Що перевіряє                                              |
| --------------------------- | --------------------------------------------------------- |
| `tests/backend/unit`        | сутності та правила: переходи станів, місткість, горизонт |
| `tests/backend/contract`    | однакова поведінка обох репозиторіїв броней               |
| `tests/backend/integration` | сценарії 1–5 зі специфікації вимог через HTTP             |
| `tests/frontend`            | екран стану кімнат і форма бронювання                     |

Час у тестах задає `FixedClock`, тому перевірки вікна відмітки про прихід і автоскасування не
залежать від реального часу й не потребують очікування. Тести репозиторію PostgreSQL запускаються,
якщо задано `TEST_DATABASE_URL` (у CI — сервіс `postgres`).
